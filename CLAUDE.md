# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Read first

Read design-docs/rustproof-spec.md and design-docs/design-delta.md before starting any task. Key rules (spec §13):

- Build Milestone 1 (examples/fib-rs) end to end, offline, before generalizing.
- Every command except login, --prover platform and beads sync must work without an account.
- The patched tree is what ships: extract, prove, test and build the same tree, and record its hash.
- Every primitive is a `rustproof step`: idempotent, content-keyed, JSON in and out.
- Never edit .rustproof/specs/, .rustproof/patches/, .rustproof/manifest.toml or .rustproof/lean/Generated/ by hand. If a spec looks wrong, stop and ask.
- Never add sorry, admit, axiom, or native_decide. `rustproof check` must pass.
- Keep crates/rustproof-core inside the Aeneas subset.
- A Python port is a patch: guarded, differential-tested, and shown as a diff. The proof is about the Rust.
- Nothing from the platform repo is a dependency.
- Back every claim with a command and its output.
- Use the status vocabulary from §7 exactly.
- Toolchains are pinned; don't upgrade them as a side effect.
- Files under `schemas/` (except `platform-api/`), `docs/cli-reference.md` and `tests/fixtures/` are generated; regenerate with `cargo xtask`, never hand-edit.
- Toolchain pins live in `rust-toolchain.toml` (the CLI's Rust) and `profiles/<id>.toml` (Charon, Aeneas, Lean); bump them only in a dedicated PR.
- `scratch/` is a planning scratch area and is never committed, except `scratch/claude-design/` (the Claude Design inputs).

## Architecture (specified)

**Pipeline.** `scan → rank → patch → extract → propose_specs → prove → check → mutate → counterexample → build → test → report` (spec §4.1; local order and approval waits in §4.3). Rust is classified `provable` / `patchable` / `excluded`, patchable functions are rewritten into the Aeneas subset by **bricks**, the patched tree is extracted to Lean 4 (Charon → Aeneas), a human approves a proposed theorem, a prover proposes the proof, and the Lean kernel checks it.

The invariants that span many files:

- **Step protocol.** Every primitive is `rustproof step <name> --json`: idempotent, content-keyed, JSON in and out (`schemas/steps/`), cached under `.rustproof/state/`. The platform's workers orchestrate the pipeline by calling these, never by re-implementing them. Ordinary commands are thin wrappers over the same steps.
- **One patched tree.** Extraction, proofs, tests and release builds all run against `target/rustproof/tree/`, whose hash is recorded as `patched_hash`. `mode = "patched-tree" | "commit"` in the manifest (`build --commit` applies patches in place and keeps the proof because `lean_hash` is unchanged).
- **Four hashes.** `source_hash` (normalized `syn` item plus workspace callees) change → `stale`; if re-extraction yields the same `lean_hash`, the proof is kept. `patched_hash` is a build stamp, not a staleness trigger. `spec_hash` pins the approved statement.
- **Trust base.** `rustproof check` is `lake build` plus policy: no `sorry`/`admit`, and `#print axioms` may show only `propext`, `Classical.choice`, `Quot.sound` and the declared signatures of that obligation's excluded callees (spec §4.5).
- **Human-owned files.** `.rustproof/specs/`, `patches/`, `manifest.toml` and `lean/Generated/` are never written by Claude. Local approvals (`pane`, `tty`) are advisory; the enforced gate is PR review under CODEOWNERS.
- **Crates.** `rustproof-core` holds the pure decisions (status machine, exit codes, policy verdict, check conclusion, manifest validation). It is written inside the Aeneas subset with no dependencies so rustproof can prove it (M6), and the platform relays its `rustproof verdict` output instead of computing verdicts. `rustproof-prover` holds the `Prover` trait (`leanstral-api`, `manual`, `platform`) and the agent loop, so there is one implementation of proof search.
- **Plugin floor vs ceiling.** Settings hooks, skills, MCP and LSP work wherever the plugin loads; the TypeScript mod (status band, `/proofs` pane, in-terminal review) only reflects CLI state and reaches the network only through the CLI (no `$.http`). Hook guards are duplicated in both layers so they hold where mods are off.
- **Contract with the platform.** `schemas/` (`steps/`, `mcp/`, `platform-api/`) is owned here; `rustproof mcp` and the platform's MCP server implement the same tool schemas and one conformance test runs both.

**Status vocabulary** (spec §7, used verbatim in CLI, JSON and UI): `proven`, `checking`, `searching`, `needs_review`, `failing`, `counterexample`, `weak_spec`, `stale`, `excluded`. **Exit codes** (§6, worst wins): `0` ok · `1` failing or counterexample · `2` policy violation · `3` needs review · `4` stale · `5` weak spec (`--strict` only) · `10` auth required.
