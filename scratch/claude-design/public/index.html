02 / THE AHA

The proof found what the tests would not.

fib(10) == 55 passes. So does fib(93). The theorem could not be proven for all of u64, and the counterexample finder said why.

fib(93)12,200,160,415,121,876,738fits in u64
fib(94)19,740,274,219,868,223,167overflows u64
theorem(h : n.val ≤ 93)

This is the spec review moment. The developer reads one sentence of English and chooses. Every option is legitimate; the point is that the system forces the decision instead of hiding it.

a
Accept the precondition
Guard it at the boundary. Callers get an error for n > 93.
b
Widen the type
u128 is good up to fib(186). Re-prove.
c
Make overflow explicit
checked_add, return Option<u64>, handle None.

05 / THE TRUST MODEL

Specs are the review surface. Proofs are not.

The proven code is the running code

rustproof proves the patched tree, and the patched tree is what gets compiled and shipped. Proofs are keyed to its hash; release artifacts are stamped with it.

Humans read theorems, never proofs

The Lean kernel rejects every invalid proof, so proof generation is fully automated. Nothing checks a spec except a person, in plain English first.

Patches are visible, tested, reversible

Every patch is a before/after diff in Claude Code, the PR and the dashboard. Both sides compile, so they run on the same generated inputs. Reject one and the function leaves the proof boundary.

No escape hatches

The build fails on sorry, on any axiom outside the approved set, and on any proof that relies on unchecked evaluation. Overflow checks stay on in release, so the binary matches the model.
