How it works

Rust → Charon → Aeneas → Lean → Leanstral → kernel.

rustproof takes a Rust crate, finds the functions whose behavior can be proven, patches them at build time into the subset Aeneas accepts, extracts to Lean 4, proposes theorems in plain English and Lean, generates proofs with Leanstral, and checks every proof with the Lean kernel.

02 / THE PROOF BOUNDARY

I/O is a boundary, not a blocker.

What gets proven

Pure, deterministic, typed functions: validation, parsing, pricing and scoring rules, data transformations, numeric kernels, state machines. In a well-structured crate, this is most of the logic.

What’s excluded

I/O, network, filesystem, clocks, randomness, global mutable state, concurrency and async, unsafe code, FFI, and anything that depends on library types Aeneas has no model for and no brick can replace. Excluded functions are visible in every surface, with the reason.

Overflow

Aeneas models arithmetic so that overflow is a failure, matching Rust’s debug builds. Release builds wrap silently. The patched build sets overflow-checks = true, so the shipped binary matches the model everywhere, and a theorem’s precondition is exactly the set of inputs on which the code doesn’t fail.

Where it lives

.rustproof/
  manifest.toml   obligations, hashes, bricks, approvals
  patches/        one patch per obligation (may be empty)
  specs/          theorem statements (CODEOWNERS)
  proofs/         generated proofs
  lean/           Lake project; Generated/ is Aeneas output
  state/          local step cache (never committed)

One set of states, every surface.

Glyphs carry the meaning on their own, so every surface works without color, including GitHub Markdown and plain terminals.

●ProvenSpec approved, proof checked by the Lean kernel, against the current patched treeNo one
